Current status

The project and the Govern record are unchanged since the 21 October review: the only new activity is temporary worksheets created and deleted on the Design node. The pipeline runs end to end. The issues are in what the gates actually enforce, how portable the governance setup is, and claims that don't match the evidence.

What works

  • 7-step app homepage drives the full flow; the last successful end-to-end run was in the dUOrLYMV instance (2026-07-28).
  • Visual-first ADaM with admiral only for baseline logic; xportr XPT v5 export; CDISC CORE 0.16.0 conformance.
  • Gates read Govern sign-offs through the built-in DSS↔Govern connection and abort builds that aren't approved.
  • Data and code fingerprints revoke every approval when anything changes, which is the strongest demo moment.

What blocks packaging

  • The SDTM gate can't fail, and the Pinnacle 21 step can be skipped.
  • Every app instance writes to the same Govern record ar.114; Govern links are hard-coded.
  • The Govern setup isn't portable: shared blueprint, named-user and API-key approvers, no admin key to export it.
  • The R environment isn't pinned; scenarios run as a former owner's personal account.
  • The deck and scoping document still claim the original scope and "Part 11 e-signatures".

Re-baselined scope

Agreed on 2026-11-05: the asset stays within what the project delivers today. Everything else from the original scoping document becomes roadmap and discovery material. The full change register and messaging guardrails are in docs/06-scope-baseline.md.

In scope (the asset)

  • SDTM lock and validation: XPT v5 export, CDISC CORE (SDTMIG 3.4), fingerprints
  • SDTM sign-off in Govern
  • ADaM derivation: ADSL, ADAE, ADREACT, ADVS, ADIS, plus 26 QC checks
  • ADaM XPT v5 export and Pinnacle 21 review (manual)
  • ADaM sign-off in Govern
  • Gated release of the XPT and TLF packages (4 summary tables)
  • Automatic revocation of approvals on data or code drift

Roadmap (from the original scoping document)

  • Raw → SDTM mapping and the raw→SDTM sign-off gate
  • EDC/API ingestion
  • Metadata-driven Global Standards Library
  • Define-XML 2.1
  • Visual-vs-code independent validation path
  • Medical review dashboards
  • QMS integration of Govern audit metadata
  • Part 11 e-signature integration; Pinnacle 21 Enterprise; full TLF suite (listings, figures, RTF); multi-study operation

Current architecture

Three lanes: the Dataiku Design node (Cloud, used for development), steps that happen outside the gated path, and the Govern node. Purple numbers trace the governance handshake; red badges point to the gaps listed below.

  1. 1build_sdtm writes the CORE result and fingerprints to Govern and opens the SDTM sign-off.
  2. 2The build_adam gate reads the SDTM approval and compares fingerprints; on drift it revokes every sign-off.
  3. 3build_adam records the ADaM fingerprint, advances the workflow and opens the ADaM sign-off.
  4. 4The presenter downloads the XPT files and runs Pinnacle 21 on a laptop.
  5. 5The Pinnacle 21 result is entered on the Govern record by hand (no report is attached).
  6. 6The release_submission gate reads both approvals and the ADaM result.
  7. 7The finalize step marks the record VALIDATED and moves it to ADaM Validated.
  8. K#Gap reference in the table below. Red dashed boxes are side paths that can change approvals: the homepage debug reset and the governance_integrity_check sweep.

Governance architecture

The governance layer is the asset's differentiator, and also the least portable part. Govern isn't an electronic-signature system (Dataiku Statement of Quality, July 2026): its sign-offs are governance approvals that a customer's Part 11 e-signature system can be linked to.

Exit criteria (definition of done)

  • A fresh instance runs end to end on its own Govern record with only the documented configuration steps
  • The SDTM gate can be shown failing, and a drift change revokes approvals
  • Release requires an attached Pinnacle 21 report and an explicit result
  • Approvals come from two different people through roles, with comments
  • The Govern blueprint exports and imports with its roles and hook
  • Both code environments are fully pinned
  • No claim in the deck, scoping document or docs contradicts the evidence or Dataiku's Statement of Quality
  • Docs 00–04 reviewed by a clinical SME; internal backlog (05) kept separate
Evidence: Dataiku Design project CLIN_FLU2026_VISUAL and app instances, Govern record ar.114 (non-admin API key), project wiki, Dataiku Statement of Quality (July 2026), and the original scoping document. Reviewed 2026-11-05. Companion documents: docs/00–06 in this repository.
